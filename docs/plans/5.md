# Plan 5 — Queue History Multi-Version, Approval Toggle, Kill Switch (DDoS Protection)

**Based on:** `context/notes.txt` L340–L347  
**Date:** October 2026  
**Status:** ✅ Fully designed, safety-audited — ready to implement

---

## Context & Motivation

Three features requested after considering public sharing of the app link (e.g., on Discord):

1. **Queue history should preserve all versions per day** — when a user regenerates their queue mid-day, the original queue (with already-solved problems) should remain visible in history.
2. **Approval required toggle** — admin can flip a switch to bypass per-user approval (open mode) or enforce it (gated mode). Currently hardcoded ON.
3. **Master kill switch** — panic button to take the entire site offline for non-admins in case of abuse/DDoS, without a redeploy.

---

## Part 1 — Design Decisions & Behavioral Semantics

### Feature 1: Queue History — Solved Queues Preserved

**Current behavior (confirmed by reading code):**
- `queue_history` table already records every generated queue, including regens as version bumps.
- `queue/history/route.ts` deduplicates to only the **latest version per date** — so earlier versions (which may contain solved problems) are invisible in the UI, even though the DB rows still exist.
- The main queue pool filter correctly excludes `SOLVED` problems from regens — this is correct and unchanged.
- The history page already has a "regenerated ×N" badge but only shows the latest queue.

**What we actually want:**
- On the history page, each date shows the latest version by default (current UX preserved).
- If there are multiple versions for a date (i.e., user regenerated), show a collapsed "↺ N older versions" toggle below the problem list.
- Expanding it shows earlier versions as sub-cards, each with their own problem list and solve bar.
- The main page (`/`) and queue generation are **not touched**.

### Feature 2: Approval Required Toggle

**Semantics:**

| User state | Approval ON (default) | Approval OFF |
|---|---|---|
| Not logged in (no cookie) | → `/login` | → `/login` (unchanged) |
| Logged in, brand-new user (no `user_access` row yet) | → `/waiting` | → App ✅ |
| Logged in, `granted=false` (pending/revoked) | → `/waiting` | → App ✅ |
| Logged in, `granted=true` | → App ✅ | → App ✅ |
| Admin (`is_admin=true`) | → App ✅ (always) | → App ✅ (always) |

**Key points:**
- Turning OFF does not change any `granted` field in the DB — it only bypasses the check in middleware.
- Turning back ON restores the old behaviour: same people who were pending/revoked are pending/revoked again.
- Admins always bypass regardless of toggle.
- Admin can still manually grant/revoke individual users regardless of the toggle state.
- **Toggle must show a confirmation dialog before saving.**

### Feature 3: Master Kill Switch

**Semantics when site is disabled:**

| User state | Behaviour |
|---|---|
| Not logged in | → `/waiting?reason=maintenance` |
| Logged in, any non-admin | → `/waiting?reason=maintenance` |
| Logged in, admin (`is_admin=true`) | → Full app access ✅ |

**Waiting page `?reason=` param:**
- `reason=pending` (default / no param): existing "Access Pending" copy — contact email, sign out.
- `reason=maintenance`: "Down for Maintenance" copy — brief message, sign-out button, plus a subtle "Admin? Sign in →" link to `/login` (for admins whose session expired while the site was off).

**Admin session expiry edge case:** If admin's session expires while site is down, they go to `/waiting?reason=maintenance`, see the "Admin? Sign in →" link, go to `/login` (always public), re-authenticate via OAuth, and get through. They are never permanently locked out.

## Part 2 — Storage & Architecture Decisions

### Storage: `system_settings` Supabase table

Single-row table. Admin reads/writes it via the admin panel. Middleware reads it on every request using the service role key.

```sql
CREATE TABLE IF NOT EXISTS public.system_settings (
  id                integer  PRIMARY KEY DEFAULT 1,
  approval_required boolean  NOT NULL DEFAULT true,
  site_enabled      boolean  NOT NULL DEFAULT true,
  updated_at        timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT single_row CHECK (id = 1)
);

INSERT INTO public.system_settings (id, approval_required, site_enabled)
VALUES (1, true, true)
ON CONFLICT (id) DO NOTHING;

ALTER TABLE public.system_settings ENABLE ROW LEVEL SECURITY;
-- No policies added: service role key bypasses RLS; anon key blocked by default.
```

### Admin panel UI

- **Sticky header** always visible above the existing tabs (Users / Analytics).
- Contains two toggles: "Approval Required" and "Site Enabled".
- Each toggle click shows a confirmation modal before saving. The "Site Enabled OFF" modal shows a red warning: *"This will block all non-admin users immediately."*
- New API route `GET/PATCH /api/admin/settings` reads/writes the `system_settings` row.
- If the settings fetch fails, toggles are disabled (greyed out) — existing Users and Analytics tabs are unaffected.

## Part 3 — DDoS Threat Analysis

### Threat model
Sharing the app link publicly (Discord) → bots or malicious users hammering free-tier resources:
- Vercel compute (serverless function invocations)
- Supabase Postgres (connection pool, query load)
- Google OAuth (sign-up spam)

### Threat surface breakdown

| Request type | Auth required? | DB hit? | Mitigated by? |
|---|---|---|---|
| Unauthenticated bot hits `/` | No | JWT decode only (local, no DB) | Middleware redirects to `/login` — zero DB hit |
| Bot signs up via Google OAuth | Google-side | 1 DB write (user_access trigger) | Google OAuth rate limits; approval required means they still can't access app |
| Authenticated-but-not-approved user hits pages | Yes | 1 `user_access` read | Goes to `/waiting` — no heavy API routes accessible |
| Approved user spams `/api/queue` regen | Yes | Heavy (full queue generation) | Kill switch can block; rate limiting if needed later |
| Unauthenticated hits `/api/queue` directly | No | Auth check only | Already returns 401 without DB work |

### Why the current setup already protects you

With `approval_required=true` (default):
- Unauthenticated requests → `/login` (zero DB).
- Authenticated but unapproved → `/waiting` (1 `user_access` read, no heavy routes reachable).
- Only explicitly approved users can hit `/api/queue`, `/api/progress`, etc.
- **This is the primary DDoS protection.** Public sharing + approval required = bots can see the login page and nothing else.

### Additional layers already present

- **Vercel CDN**: handles extreme floods at the edge before your serverless functions run.
- **Google OAuth rate limits**: mass sign-up bots can't easily create accounts.
- **Supabase RLS**: unauthenticated DB queries from the anon key hit RLS policies and return nothing for user-scoped tables.

### Kill switch role

The kill switch is a **panic button for casual abuse**, not a DDoS mitigation. Real DDoS at scale is handled by Vercel's infra. The kill switch is for scenarios like:
- A trusted user is generating thousands of queue regens in a loop.
- Someone shared the link to people you haven't vetted yet and you want to pause.

## Part 4 — Safety Audit (Production)

Six risks identified and resolved before coding.

### 🚨 Risk 1 — Module-level cache banned in Next.js 16 Proxy/middleware

Next.js 16 deprecated `middleware.ts` → `proxy.ts` and explicitly states:
> *"you should not attempt relying on shared modules or globals"*

The original plan proposed a 90-second module-level TTL cache for `system_settings`. This is **not safe** — module-level variables in the Edge runtime are per-isolate and unreliable across CDN nodes.

**Resolution:** No caching. Middleware reads `system_settings` with a fresh service-role client on every request. It's a single-row PK lookup (~5–10ms). Acceptable on Supabase free tier.

Safe fallback: if the DB read fails for any reason, defaults to `{ approval_required: true, site_enabled: true }` — the most restrictive values. The app never accidentally opens due to a DB hiccup.

### ⚠️ Risk 2 — `middleware.ts` is deprecated in Next.js 16

The rename (`middleware` → `proxy`) is noted. **Not migrating now** to keep this PR minimal and safe. Follow-up: separate commit, rename only, zero logic change.

### ⚠️ Risk 3 — `useSearchParams` requires `<Suspense>` in Next.js 16

The Next.js 16 docs require wrapping `useSearchParams` in a `<Suspense>` boundary for prerendered routes. Using it naively in `/waiting/page.tsx` would cause a build warning or prerender bailout.

**Resolution:** Use `window.location.search` directly (native browser API). Safe because `/waiting/page.tsx` is already `'use client'` with `supabase.auth.signOut()` — fully client-rendered, no SSR involved.

```ts
const reason = typeof window !== 'undefined'
  ? new URLSearchParams(window.location.search).get('reason')
  : null;
```

### ⚠️ Risk 4 — History API shape change must deploy atomically with the page

The history API response shape changes (`HistoryEntry` → nested `{ versions: [...] }`). The existing page accesses `entry.solved_count` directly, which would throw on the new shape.

**Resolution:** Steps 4 and 5 (API route + page) must be in the same git commit and deployed together. Also adding `latest_solved_count` / `latest_total_count` as top-level convenience fields — so any partial mismatch results in `0/0` display rather than a crash.

### ⚠️ Risk 5 — Admin session expiry while kill switch is ON

If admin's session expires while the site is off, `getUser()` returns null → middleware redirects to `/waiting?reason=maintenance` → admin appears stuck.

**Resolution:** `/login` and `/auth/callback` are already in `PUBLIC_PATHS` (always accessible). Waiting page shows a subtle "Admin? Sign in →" link to `/login`. Admin can re-authenticate via OAuth and return to the app.

### ✅ Risk 6 — `system_settings` with no RLS policies

Confirmed safe. Service role key bypasses RLS. Anon key blocked by default with no policies. No user-facing code reads this table directly.

### Step 2 — `middleware.ts` detailed diff

Add helper above the middleware function:

```ts
async function getSystemSettings(supabaseUrl: string, serviceKey: string) {
  try {
    const client = createClient(supabaseUrl, serviceKey, { auth: { persistSession: false } });
    const { data } = await client
      .from('system_settings')
      .select('approval_required, site_enabled')
      .eq('id', 1)
      .single();
    return data ?? { approval_required: true, site_enabled: true };
  } catch {
    return { approval_required: true, site_enabled: true }; // safe fallback
  }
}
```

In the middleware function body, after `const isPublic` line:

```ts
const settings = await getSystemSettings(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!
);
```

Add kill-switch block (after above, before existing whitelist check):

```ts
if (user && !isPublic && !settings.site_enabled) {

    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!,

  // Admin: fall through to normal flow
}
```
