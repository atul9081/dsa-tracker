### 🔴 Fix 1: Reveal UX Rewrite (`components/ProblemCard.tsx`)

**Final design (Option A — blur/unblur):**

**TO_DO state:**
- Title visible, `🔒 topic hidden` badge visible, description rendered but **CSS-blurred**
- Small blurred block (max-height capped so it's compact, not a full-length blurred wall)
- "👁 Reveal" button visible

**On first "Reveal" click:**
- Description unblurs (full height, readable)
- Timer starts, status → ATTEMPTING (DB call)
- Button changes to "🙈 Hide"
- This is **one-time** — subsequent Hide/Reveal clicks don't touch status or timer

**On subsequent Hide clicks:**
- Description re-blurs AND **compresses back to compact size** (same cap as initial state)
- Button changes back to "👁 Reveal"
- No status/timer side effect

**On subsequent Reveal clicks:**
- Description expands + unblurs again
- No status/timer side effect

**`↗ Solve` link:**
- If currently TO_DO, clicking it also triggers the same "first reveal" action (start timer + ATTEMPTING) before opening the tab
- If already ATTEMPTING, just opens the tab

**ATTEMPTING state:**
- Same card design: description visible (unblurred) with the Hide/Reveal toggle still usable
- Timer ticking, `🔄 Attempting` badge
- Description toggle persists across the status change (no re-mount reset)

**SOLVED state:**
- Description shown collapsed with "View problem / Hide problem" toggle (unchanged from current)
- DifficultyBadge + TopicTags revealed

**Key implementation note:**
- `revealed` state = boolean, persists for the component lifetime
- `descVisible` state = boolean (toggled by Hide/Reveal after first reveal), default = `revealed`
- The compact blurred block: `max-height: 80px; overflow: hidden; filter: blur(8px); cursor: pointer`
- The expanded readable state: `filter: none; max-height: none`
- Show more/less for long descriptions (>1200 chars) only applies when description is **visible** (not blurred)

**Link text:** Change all "Open on LeetCode ↗" → **`↗ Solve`** across ProblemCard.tsx. Use `problem.external_url` if set (CSES), else construct LC URL from `title_slug`.

### 🔴 Fix 2: Difficulty Leak — DOM-Aware Sanitize (`components/ProblemCard.tsx`)

Replace current regex-based `sanitizeDescription` with a DOMParser-based version:

```ts
function sanitizeDescription(html: string): string {
  if (typeof window === 'undefined') return html;
  const doc = new DOMParser().parseFromString(html, 'text/html');
  const DIFFICULTY_RE = /^(Difficulty\s*:\s*)?(Easy|Medium|Hard)$/i;
  doc.querySelectorAll('*').forEach(el => {
    if (el.children.length === 0 && DIFFICULTY_RE.test(el.textContent?.trim() ?? '')) {
      el.remove();
    }
  });
  return doc.body.innerHTML;
}
```

Removes any leaf element whose sole text content is a difficulty label, regardless of HTML structure.

#### 5d. Selection Algorithm — Detailed Design

**Goal:** Diverse, fair, historically-aware queue that:
1. Weighs topics by OLT importance
2. Weighs sub-types by staleness (days since last practiced)
3. Respects user's enabled topics + platform selection
4. Never repeats a sub-type within a single day's queue
5. Is not skewed by dataset size

##### 3-Stage Weighted Selection with Cooldown

---

**Pre-computation (once per queue generation):**

```ts
const today = new Date();
const COOLDOWN_MAX = userSettings.cooldown_days ?? 7;  // configurable

// Fetch last solved date per sub-type (last 30 days)
const recentSolves = await supabase
  .from('user_progress')
  .select('updated_at, problems!inner(sub_type, topic_tags)')
  .eq('status', 'SOLVED')
  .eq('user_id', userId)
  .gte('updated_at', subDays(today, 30));

// Build: subtype → most recent solved date
const lastSolvedBySubtype: Record<string, Date> = {};
for (const row of recentSolves) {
  const st = row.problems?.sub_type;
  if (!st) continue;
  const d = new Date(row.updated_at);
  if (!lastSolvedBySubtype[st] || d > lastSolvedBySubtype[st])
    lastSolvedBySubtype[st] = d;
}

function stalenessScore(subtype: string): number {
  const last = lastSolvedBySubtype[subtype];
  if (!last) return 1.0;  // never practiced = fully stale = highest priority
  const days = (today.getTime() - last.getTime()) / 86_400_000;
  return Math.min(days, COOLDOWN_MAX) / COOLDOWN_MAX;
  // → 1.0 at 7+ days, 0.0 at solved today
}
```

---

**Stage 1 — Topic selection:**

```
eligible_topics = enabled_topic_slugs ∩ topics_with_unsolved_problems
topic_weight(t) = olt_score(t)^2 × user_topic_weight_override(t, default=1.0)
```

Pick topic T via weighted random. Mark T as "used" (max 3 per day, existing guard).

**Note:** Dataset normalization is preserved — we sample the TOPIC first (not the problem directly), so a topic with 500 problems doesn't outweigh one with 50.

---

**Stage 2 — Sub-type selection:**

```
eligible_subtypes = SUBTYPES[T] where:
  - at least 1 unsolved problem exists in this sub-type
  - this sub-type NOT already used today (max 1 per sub-type per day)

subtype_weight(st) = staleness(st)
  // base_weight = 1.0 (uniform); staleness alone drives the selection
```

Pick sub-type ST via weighted random. Mark ST as "used for today".

If no eligible sub-type for topic T → try next topic.

---

**Stage 3 — Problem selection:**

```
problem_pool = unsolved problems where:
  - primary_topic = T (from getPrimaryTopic())
  - sub_type = ST
  - source IN user.enabled_sources (e.g., ['leetcode', 'cses'])
  - paidOnly = false

problem_weight(p) = difficulty_multiplier(p.difficulty)
  // difficulty_multiplier: HARD=3, MEDIUM=2, EASY=1 (configurable in queue.ts)
```

Pick problem P uniformly from `problem_pool` (or weighted by difficulty if multiple difficulty levels available).

---

**Platform interleaving:**

When both LC and CSES enabled, the target split is proportional to their enabled problem counts:

```
cses_count = count of unsolved CSES problems in enabled topics
lc_count   = count of unsolved LC problems in enabled topics
cses_slots = round(dailyCount × cses_count / (cses_count + lc_count))
lc_slots   = dailyCount - cses_slots
```

Generate `lc_slots` problems from LC pool and `cses_slots` from CSES pool separately (each using the same 3-stage algorithm), then shuffle the combined list.

---

**Fallback chain:**

```
1. Stage 2 fails (no eligible sub-type in picked topic):
   → Try next-best topic (next in weighted ranking, not fully random)
   
2. Stage 3 fails (no unsolved problems in this sub-type):
   → Try next-best sub-type in same topic
   
3. Entire topic exhausted:
   → Skip topic, try next

4. All topics exhausted or fewer problems than dailyCount:
   → Relax sub-type uniqueness (allow same sub-type twice)
   → If still short: relax topic uniqueness (allow >3 per topic)
   → If still short: show "🎉 You've completed enough problems in these topics! Consider enabling more topics." instead of filling
```

---

**Summary of changes vs current algorithm:**

| | Current | New |
|--|---------|-----|
| Stages | 2 (topic → problem) | **3 (topic → sub-type → problem)** |
| Sub-type awareness | None | Staleness cooldown (7-day window) |
| Dataset skew guard | Topic-normalized | Topic-normalized **+ sub-type normalized** |
| Same-topic guard | Max 3/day | Max 3/topic, **max 1/sub-type** |
| Solved problems | Permanently excluded | Permanently excluded (no revision for now) |
| Platform mixing | LC only | LC + CSES, proportional slots |
| Topic settings | Respected | Respected + CSES/LC platform toggle |
