## Comprehensive Edge Case Map

### User Lifecycle States

A user can be in one of 5 states:

| State | user_access row | granted | is_admin | Description |
|---|---|---|---|---|
| **Pending** | exists | false | false | Signed up, not yet reviewed |
| **Granted** | exists | true | false | Approved by admin |
| **Revoked** | exists | false | false | Was reviewed and explicitly denied (or had access removed) |
| **Admin** | exists | any | true | is_admin=true, always passes |
| **Orphaned** | missing | — | — | Row was deleted (Remove clicked) or trigger failed |

### Behavior Matrix: Middleware Decision

| State | approval=ON, site=ON | approval=OFF, site=ON | site=OFF |
|---|---|---|---|
| Pending | → /waiting | → / (allowed, never reviewed) | → /waiting?reason=maintenance |
| Granted | → / | → / | → /waiting?reason=maintenance |
| Revoked | → /waiting | → /waiting (**blocked**) | → /waiting?reason=maintenance |
| Admin | → / | → / | → / (bypasses kill switch) |
| Orphaned | → /waiting | → / (no row = not reviewed) | → /waiting?reason=maintenance |

> [!IMPORTANT]
> **D3 enforced here:** When approval=OFF, only Pending and Orphaned get through. Revoked stays blocked — the admin made an explicit decision about them that should survive a global toggle.

### /waiting Page Behavior

| Logged-in? | site=OFF | approval=ON, not granted | approval=OFF, revoked |
|---|---|---|---|
| No session | Shows maintenance copy | (can't reach /waiting without being sent here) | — |
| Session, not admin | Shows maintenance copy | Shows pending copy | Shows pending copy |
| Session, admin | Middleware redirects to `/` immediately | Middleware redirects to `/` | Middleware redirects to `/` |

### Auth Callback Edge Cases

| Scenario | What happens |
|---|---|
| Google OAuth, new user | trigger → user_access row (granted=false, email, display_name from Google) |
| Email signup, new user | trigger → user_access row (granted=false, email set, display_name=null since no full_name in metadata) |
| Previously removed user re-authenticates | auth/callback upsert with `ignoreDuplicates=true` → new row created (granted=false) → appears in Pending again |
| Previously granted user re-authenticates | auth/callback upsert with `ignoreDuplicates=true` → existing row unchanged (granted=true preserved) ✅ |
| Trigger race condition (row not yet committed at middleware time) | treated as Pending → /waiting. Next request: row exists. ✅ |

### Admin Panel Edge Cases

| Action | Guard | Outcome |
|---|---|---|
| Remove a granted user | DELETE route: returns 400 if granted=true or is_admin=true | Blocked ✅ |
| Remove a pending user | DELETE allowed | Row deleted → user goes Orphaned |
| Remove an admin | DELETE route: returns 400 if is_admin=true | Blocked ✅ |
| Grant by email (signed up) | POST finds in auth.users → upsert granted=true | Creates/updates row ✅ |
| Grant by email (not signed up yet) | POST returns 'not_signed_up' message | Shows message to admin ✅ |
| Grant a removed user from Removed section | Same as "Grant by email" behind the scenes | Re-creates row with granted=true |
| Admin self-demotes (removes own is_admin) | No guard currently | Would lock admin out of /admin on next request ⚠️ |

> [!WARNING]
> **Admin self-demote is unguarded.** If an admin updates their own `is_admin=false` from the admin panel, they lose access immediately on next request. Considered acceptable for now (small team, DB access available as recovery).

### Toggle Interaction Scenarios

| Sequence | Result |
|---|---|
| Approval OFF → revoked user refreshes /waiting | Stays on /waiting (D3) |
| Approval OFF → pending user refreshes /waiting | Redirected to / ✅ |
| Site OFF → admin refreshes /waiting | Redirected to / ✅ |
| Site OFF → non-admin clicks any navbar link | Middleware fires → /waiting?reason=maintenance |
| Site ON again → user on /waiting?reason=maintenance refreshes | Redirected to / ✅ |
| Both OFF → non-admin | Maintenance page (site_enabled takes priority) |
| Both OFF → admin | Passes through (admin bypass) |
| Approval ON → OFF → ON | Revoked users: blocked → blocked → blocked (state preserved). Pending: blocked → through → blocked. |

### Display Name Cases

| Signup method | display_name in user_access | Admin panel display |
|---|---|---|
| Google OAuth | `full_name` from metadata | Name + email below |
| Email+password | null (no name metadata) | `—` + email below |
| Old user (pre-migration) | null (trigger didn't capture) | `—` + email below (after SQL fix) |
| Old user (email as fallback — old bug) | equal to email | `—` + email below (API route no longer falls back to email for display_name) |

## Remaining Issues Found (post Plan 6)

### Issue R1 — chapterism22@gmail.com still shows pending

**Why:** User was Removed (row deleted). No user_access row. The Plan 6 middleware fix correctly sends them to `/` when approval=OFF. But:
1. They may have tested before Vercel deployment was live.
2. They're currently in **Orphaned** state — if approval is back ON, they correctly see /waiting.

**Recovery path (NOW):** Admin types `chapterism22@gmail.com` in "Grant access by email" box → Grant. This calls POST /api/admin/users → finds them in auth.users → creates `user_access` row with `granted=true`. Done.

**Long-term fix:** Plan 6.1 adds a "Removed" section in admin panel so orphaned users are visible and re-grantable without knowing their email.

### Issue R2 — display_name = email (name shows twice)

**Why:** `authEmailMap` fallback in API route uses email for display_name when it's null. New users with no Google name (or email signup) get email as their display_name.

**Fix:** API route uses `user_metadata.full_name` or `.name`, NOT email, as display_name fallback. UI `displayName()` returns `'—'` when null.
