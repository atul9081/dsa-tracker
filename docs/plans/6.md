## Bug Inventory

### Bug 1 — `/waiting` is a dead end for logged-in users (root of most reported issues)

**Symptom:** 
- Admin flips "Approval Required" OFF → pending user sitting on `/waiting` still sees "Access Pending". Only manually typing `/` fixes it.
- Admin re-enables site → user on `/waiting?reason=maintenance` refreshes and still sees "Down for Maintenance".
- Site is disabled → user already on `/waiting` (pending) still shows "Access Pending" copy instead of maintenance copy.

**Root cause:**  
`/waiting` is in `PUBLIC_PATHS` → middleware unconditionally passes through, never re-evaluates the user's actual access. The page renders whatever `?reason=` is in the URL — it doesn't check if that reason is still valid.

**Fix — middleware.ts:**  
Add a dedicated `/waiting` intercept block for logged-in users (runs before the generic public path passthrough):

```
if pathname starts with /waiting AND user is logged in:
  fetch user_access.granted + is_admin (service role)

  if site disabled (kill switch ON):
    if admin → redirect to /          (admin always gets through)
    if not admin → ensure URL has ?reason=maintenance, render
  
  if site enabled:
    if approval_required=false OR user is granted/admin → redirect to /
    if approval_required=true AND not granted:
      if URL has ?reason=maintenance → remove it (site is back, fix stale param)
      render (correctly pending)
```

Unauthenticated visitors are unaffected — they hit `/waiting` without a session and fall through to `supabaseResponse` as before.

### Bug 2 — `reason` param not reactive on the waiting page

**Symptom:**  
User is on `/waiting` (reason=pending). Middleware redirects them to `/waiting?reason=maintenance`. Component is already mounted — `reason` variable doesn't update → still shows "Access Pending" copy.

**Root cause:**  
```ts
// Evaluated once at initial render, never re-runs
const reason = typeof window !== 'undefined'
  ? new URLSearchParams(window.location.search).get('reason')
  : null;
```
When Next.js does a client-side navigation back to the same route with a different URL, the component isn't remounted, so this line never re-executes.

**Fix — waiting/page.tsx:**  
Move into `useEffect` + state:
```ts
const [reason, setReason] = useState<string | null>(null);
useEffect(() => {
  setReason(new URLSearchParams(window.location.search).get('reason'));
}, []);
```
Note: after middleware fix (Bug 1), the middleware corrects the URL on every request, so most stale-reason cases are already resolved server-side. But this client-side fix handles the remaining edge case where the component is already mounted.

### Bug 3 — "Admin? → Sign in" shown to all users, including logged-in non-admins

**Symptom:**  
A regular user on `/waiting?reason=maintenance` sees:
- "Sign out" button (correct — they are logged in)
- "Admin? → Sign in" link (wrong — they are not an admin, and they're already signed in)

After sign-out, going to `/` redirects to `/waiting?reason=maintenance`. The user now sees:
- "Sign out" button (wrong — they have no session)
- "Admin? → Sign in" link (correct — but redundant alongside the sign-out button)

**Root cause:**  
Waiting page doesn't know if the user is logged in. It always renders both elements when `isMaintenance=true`.

**Fix — waiting/page.tsx:**  
Check session on mount:
```ts
const [isLoggedIn, setIsLoggedIn] = useState(false);
useEffect(() => {
  const supabase = createBrowserClient(...);
  supabase.auth.getSession().then(({ data: { session } }) => {
    setIsLoggedIn(!!session);
  });
}, []);
```
Then:
- Sign-out button: render only if `isLoggedIn`
- "Admin? → Sign in" link: render only if `!isLoggedIn && isMaintenance`

### Bug 7 — `problems_with_status` Security Definer warning in Supabase

**Warning text:**  
*"This view is defined with the Security Definer property, giving it permissions of the view's creator (Postgres)... Data is publicly accessible via API as this is a Security definer view."*

**Analysis:**  
The view is defined in `phase4.sql` WITHOUT `SECURITY DEFINER` explicitly. Supabase adds it automatically for views that reference `auth.uid()`. The view JOIN is:
```sql
LEFT JOIN user_progress up
  ON up.problem_id = p.id
  AND up.user_id = auth.uid()
```
Even with Security Definer, `auth.uid()` resolves to the **calling user's ID** at query time. User A cannot see user B's progress rows — the JOIN filters them out. The `problems` table data (title, difficulty, etc.) is intentionally public.

**Verdict:** Not an actual data leak. The Supabase UI warning is overly broad — it fires whenever a Security Definer view exists in `public`, regardless of whether `auth.uid()` scoping makes it safe.

**Fix — SQL:**  
Recreate the view with `security_invoker = true`. This tells Postgres to apply RLS using the caller's identity, eliminating the warning and adding defense-in-depth:

```sql
DROP VIEW IF EXISTS problems_with_status;
CREATE VIEW problems_with_status
  WITH (security_invoker = true)
AS
SELECT
  p.id, p.title, p.title_slug, p.difficulty, p.topic_tags,
  p.description, p.ac_rate, p.paid_only, p.olt_score,
  p.sub_type, p.source, p.external_url,
  COALESCE(up.status, 'TO_DO')  AS status,
  up.updated_at                  AS status_updated_at,
  up.attempt_started_at,
  up.solve_duration_secs,
  up.first_attempted_at
FROM problems p
LEFT JOIN user_progress up
  ON up.problem_id = p.id
  AND up.user_id = auth.uid();
```

### Bug 8 — Null `email`/`display_name` in `user_access` for some users

**Affected user:** `b62298a9-96ee-4032-9130-7093c56178e6` (`harshwantstolearncode@gmail.com`)  
Also affects any user who signed up before `admin_panel.sql` migration ran (trigger only inserted `user_id + granted`, no email/name).

**Root cause:**  
Old trigger (from `phase4.sql`) only wrote `user_id + granted`. New trigger (from `admin_panel.sql`) writes `email + display_name` too. Users who signed up in the gap between these two migrations have null email/display_name in `user_access`.

**Fix — two parts:**

**Part A — SQL backfill:**
```sql
UPDATE user_access ua
SET
  email        = COALESCE(ua.email, u.email),
  display_name = COALESCE(
    ua.display_name,
    u.raw_user_meta_data->>'full_name',
    u.raw_user_meta_data->>'name',
    u.email  -- last resort: use email as display name
  )
FROM auth.users u
WHERE ua.user_id = u.id
  AND (ua.email IS NULL OR ua.display_name IS NULL);
```

**Part B — Admin API fallback:**  
The `/api/admin/users` route already calls `adminSupabase.auth.admin.listUsers()`. Build an `authEmailMap` from it and use it as fallback for rows where `user_access.email IS NULL`:

```ts
const authEmailMap: Record<string, string> = {};
if (authUsers) {
  for (const u of authUsers.users) {
    lastSignInMap[u.id] = u.last_sign_in_at ?? null;
    authEmailMap[u.id]  = u.email ?? '';
  }
}
const users = (accessRows ?? []).map(row => ({
  ...row,
  email:        row.email        ?? authEmailMap[row.user_id] ?? null,
  display_name: row.display_name ?? authEmailMap[row.user_id] ?? null,
  last_sign_in: lastSignInMap[row.user_id] ?? null,
}));
```
